## 1. 跨周候选身份混用，重复周会覆盖正确 ε（优先级最高）

位置：[PricePredictionService.cs](../src/EndfieldPriceOverlay/Services/PricePredictionService.cs)，`AnalyzeConsecutiveWeeks`，约 199～268 行。

每一轮的 `SourceTemplate.Id` 属于该轮来源周。周模板可以改变，因此不同轮的相同 ID 并不天然代表同一个 ε 假设。但实现直接按 ID 求交集；交集为空则保留旧候选，冲突证据被跳过。

更直接的故障是：两周价格完全相同，对任意来源模板做“反推再还原”都能得到零残差。代码用较小的单轮残差替换旧候选；之前正常跨模板预测因整数取整有极小非零误差，就会被这个零残差覆盖。新 ε 实际上来自错误模板坐标，后续却仍当作已经校准的 ε 使用。`fullEpsilon` / `candidateEpsilon` 还会把最新完整周套进旧的来源模板，存在同样的归属问题。

**真实例子：武侠电影货组。** 6/29 周到 7/6 周匹配为模板 `7→6`；7/6、7/13 连续两周完全相同，零残差自匹配覆盖了来源 7 的 ε。7/20 周只看周一时，应用声称确定，把 7/25 预测为 **4333，实际 1000，误差 333.3%**。补到周三后虽变为多候选，真实曲线仍不在其中。

为排除 OCR 干扰，用算法自身 `Predict` 和固定 ε 生成整数价格，枚举 512 种模板组合，仅开放最后一周前三天：

| 合成场景 | 单一存活走势 | 单一走势中存在未来误差>5% | 没有任何存活曲线完整命中未来（容差1） |
|---|---:|---:|---:|
| 三周，模板 A→B→C | 500 | 2 | 10 |
| 中间重复一周，A→B→B→C | 187 | **18** | **333** |

重复周探针没有录入噪声，证明实现本身有缺陷。上述计数是故障探针结果，不代表市场发生概率。

**修复方向：** 给候选保留来源周与模板路径，或直接按一致的 ε 假设累计各周证据；重复周只能说明价格重现，不能重新识别 ε；不能凭某一轮最小残差永久替换全历史校准；矛盾时重新评估而非跳过。

## 2. “唯一剩余”被当作“确定正确”，缺少拒绝预测机制

位置：[PricePredictionService.cs](../src/EndfieldPriceOverlay/Services/PricePredictionService.cs)，92、117、121 行附近；[PredictionStatusService.cs](../src/EndfieldPriceOverlay/Services/PredictionStatusService.cs)，122 行附近。

`threshold = max(最小残差 × 5, 0.003)` 总会保留最优者，即使所有候选都不合格。0.003 是**相对误差平方的均值**，其平方根约为 5.48%，并非 0.3% 误差。候选越差，动态门槛还会越宽。状态层仅凭存活曲线数为 1 就显示“本周走势已确定”，没有独立的拟合质量门槛。

主样本中，周一 63 次 Ready 有 **19 次**至少一个未来价格误差超过 5%；周三 157 次 Ready 仍有 **12 次**。例如选剑铸炉货组在 9/1 给出 Ready，预测 9/6 为 **959，实际 1919**。

另外，只要最低残差小于 `1e-9`，`Confidence` 就给**所有候选**赋值 1，连有误差或已淘汰的候选也不区分；这个值不是校准后的正确概率。

**修复方向：** 独立设置绝对拟合门槛和单日误差约束；所有候选失配时允许拒绝预测、撤销锁定；确定性须由回测校准，不能单凭唯一性。周一至少应保留合理的模板歧义。

## 3. 候选包络不是可靠的价格上下界，会影响购买建议

位置：[PredictionStatusService.cs](../src/EndfieldPriceOverlay/Services/PredictionStatusService.cs)，140 行附近；[PurchaseRecommendationService.cs](../src/EndfieldPriceOverlay/Services/PurchaseRecommendationService.cs)，约 169～178 行。

目前直接取候选最小值、最大值形成区间，没有包含 ε 估计误差和模型误差。一旦真实候选在前面被排除，宽区间也可能整体落在错误位置。

武侠电影货组以 7/22 为截止日，之后四天的真实价格**全部不在区间内**：

| 日期 | 预测区间 | 实际 |
|---|---:|---:|
| 7/23 | 2400～5500 | 1200 |
| 7/24 | 877～1988 | **4295** |
| 7/25 | 2400～6933 | 1000 |
| 7/26 | 520～1606 | 3502 |

周三未确定的 184 个未来点，严格区间覆盖率仅 **48.37%**，允许上下边界各误差 1 后也只有 **50.00%**，问题不只是取整。购买建议把区间最大值当作保守成本；这里的“上限”低于实价，无法保证保守。本次未进一步回测实际购买支出。

**修复方向：** 先修候选，再按样本外误差建立区间并报告覆盖率；失配区间不应作为可信上限输入购买分配。

## 4. 固定 ε 线性公式无法解释部分重复实价

位置：[PricePredictionService.cs](../src/EndfieldPriceOverlay/Services/PricePredictionService.cs)，`ComputeEpsilon` / `Predict`，约 19～46 行。

悬空鼷兽骨雕货组从较早完整周反推 ε，前两天匹配正确时，对 8/1 的预测是 **395，实际 630**；9/5 再次出现同样的预测和实价。武陵冻梨货组 7/31 预测 **5486，实际 4590**；4590 在另外两周也出现。冬虫夏笋货组 7/18 预测 **5786，实际 4604**。

这些现象与极端价格存在截断或饱和相符，提示当前公式可能缺少边界规则；**仅凭当前记录尚不能确认游戏的具体上下限公式**，仍需核对原始读数。不能简单把所有误差都归因于周模板识别或 OCR。

当前只把 ε 截在 `[-0.5, 0.5]`，不保证输出满足应用录入的 300～5500 范围。主样本中有 14 个 Ready 未来预测点超出该范围。这里是应用自身输入输出约束不一致，并不据此断言游戏真实边界就是 300 / 5500。

**修复方向：** 单独研究重复极值和不同模板系数间的偏差；对疑似截断点采用相应约束，避免直接反推成真实 ε。只截断输出到历史最小/最大值可能掩盖错误，不能作为未经验证的最终规则。

## 历史窗口对照与修复顺序

只保留上周及本周已知数据，算法不变：周三 Ready 从 **157/203 增到 173/203**，未确定区间覆盖率从 **48.37% 增到 90.83%**。武侠电影 7/22 案例的四个未来预测变为 `1200、4295、1000、3501`，实际为 `1200、4295、1000、3502`。

但该对照的周三 Ready MAPE 从 0.52% 变为 0.65%，且 Ready、区间各自评价的样本发生变化。因此它是“旧历史处理有害”的诊断证据，**不是直接删历史即可上线的证明**。

建议依次修复：候选身份及重复周覆盖 → 失配拒绝与状态置信度 → 极值公式 → 区间与购买成本传播。每一步都复用相同回测口径，保留后续新周作为未参与调参的验证集。

## 复现与限制

运行方法见 [回测工具说明](../scripts/PredictionBacktest/README.md)。本次完整逐日对比、每周统计和追踪结果位于本地 `artifacts/prediction-backtest/`，原始价格及数据库副本被 Git 忽略。

- `summary.md` / `summary.csv`：完整统计、基线与历史窗口对照。
- `points.csv`：每个物资、截止日、目标日的预测/实际/区间。
- `diagnostics.json`：错误案例的逐轮候选及合成探针。
- `backtest.json`：全部原始回测输出。

原有预测、状态和购买建议相关测试 **17/17 通过**，但它们未覆盖此次发现的带取整重复周污染和真实样本滚动回测。回测工具另外检查了未来日期隔离、目标日期对齐，以及主样本两种回放口径的一致性。

`PredictionStatusService.Get(item, day)` 并不自动隐藏 `day` 后的数据库价格，直接对完整数据库传历史日期会泄漏未来信息。本次通过独立截断数据库避免了这一点。

实际值来自现有合并记录，尚未重新核对游戏截图；`daily_prices` 覆盖写入前的版本没有保存，录入时间回放只能使用仍留存的版本。不同截止日窗口重叠、同一物资和重复模板相关，预测点不能当作独立样本。当前结论描述这一本地账户的历史，不直接推广到所有账户。
